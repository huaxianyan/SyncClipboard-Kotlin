# 架构说明

## 模块

项目由三个 Gradle 模块组成：

| 模块 | 职责 |
| --- | --- |
| `app` | 主体应用，负责界面、配置、协议、网络、文件处理、Hash 校验和同步记录 |
| `bridge-api` | 主体应用与系统扩展共用的 AIDL 接口及协议常量 |
| `system-extension` | 注入 SystemUI 的无界面 LSPosed 扩展，只负责访问系统剪贴板和转发设备锁定状态 |

主体应用是唯一的配置和业务中心。系统扩展不保存服务器配置，不访问网络，也不维护数据库、历史记录或通知。

## 手动同步

快速设置磁贴和 Android 分享使用轻量原生 Activity，不启动 Compose 页面：

```text
SystemUI／Android 分享
→ TileActionActivity
→ ClipboardTransferService
→ SyncClipboardClient
→ SyncClipboard Server
```

上传时先写入数据文件，再更新 `SyncClipboard.json`，避免元数据指向尚未存在的文件。下载时根据内容类型写入剪贴板或系统下载目录。

## 自动同步

高级自动同步由 SystemUI、主体应用的独立进程和服务器共同完成：

```text
本地复制文本
→ SystemUI 扩展
→ Binder
→ 主体 :sync 进程
→ SyncClipboard Server

RemoteProfileChanged
→ 主体 :sync 进程
→ 类型过滤与 Hash 校验
→ SystemUI 剪贴板或 SAF 保存目录
```

自动上传目前只处理文本。图片和文件由 Android 分享入口手动上传。远端图片与文件可以自动接收，并分别写入用户通过 Storage Access Framework 选择的目录。

系统扩展写入远端文本时会抑制对应的本地回调，主体进程还会比较「上次同步点」避免远端内容被反向上传；而要不要把远端内容写进剪贴板，由「本机剪贴板登记值」决定，见下文「下载去重判据」。

## 网络生命周期

远端更新以 SignalR WebSocket 为主要通道，并限制为 WebSockets 传输。连接建立后会立即补查一次远端状态。

运行策略：

- 设备解锁且网络条件满足时连接
- 锁屏后断开连接
- 网络恢复后立即重连
- 连接失败后按 `5 秒 → 15 秒 → 30 秒 → 1 分钟 → 2 分钟 → 5 分钟`退避
- SignalR 不可用时，HTTP 补查最多每 5 分钟执行一次；补查或恢复基线失败只进入错误状态和退避重试，不会终止 `:sync` 进程
- 不持有 WakeLock，不设置 Alarm，不使用前台服务
- 开启「仅通过 Wi-Fi 自动同步」后，移动网络期间停止自动上传、SignalR 和 HTTP 补查

Pixel 的息屏显示状态下，屏幕可能仍被系统报告为可交互。因此真实锁定状态由 SystemUI 中的 `KeyguardManager.KeyguardLockedStateListener` 转发，主体进程不依赖普通屏幕广播判断锁屏。

## 暂停与恢复边界

「接收暂停期间的云端更新」默认开启，恢复自动同步时会接收服务器当前仍保留的最新内容。关闭后，恢复时不再把服务器当前那份内容写进剪贴板，由两条判据共同决定：

- **内容时间（主判据）**：官方服务端的历史记录接口 `GET /api/history/{Type}-{Hash}` 返回内容首次到达云端的时刻 `createTime`。**只在补查路径上生效**（连接建立后的那次查询、实时通道不通时的定时补查）：补查时若它早于本次判定时刻（宽限 5 秒），说明这份内容是本机看不到云端的窗口里积压的，只归档进文本历史、不写剪贴板。判定只用「这一刻」这一把尺子，不需要知道那个窗口是**为什么**出现的。实时推送不套用判据：推送只由别的设备刚改完云端触发，本身就是内容「刚刚」到达的证据。
- **为什么推送不能判**：`createTime` 是记录**首次**创建的时刻，重复上传不会刷新它（服务端 `AddProfile` 命中已有 hash 时只刷 `LastAccessed`/`LastModified`/`Version`，`PATCH` 与 `UpdateEntityFields` 也都不碰它）。所以「重新复制一条以前复制过的内容」在时间上与一条积压内容无法区分，只能靠调用时机区分：补查可能有积压，推送必然是刚刚。
- **远端基线（降级路径）**：服务端不提供内容时间时（老版本、纯 WebDAV 部署、时钟偏移超出可信范围）回落到基线对齐，行为与旧版一致。

两条判据都要求关闭「接收暂停期间的云端更新」；该开关开启时不拦截任何内容。时间判据所需的服务器时钟偏移在循环启动时独立校准，不再依赖是否建过基线——否则基线一旦漏判，判据会跟着一起失效。

被跳过的内容记一条 `stale_write_skipped` 诊断事件（带它比判定时刻旧了多少毫秒），文本历史开启时同时归档进历史：剪贴板保持干净，内容也不会因为「没写剪贴板」而彻底丢失。

**不再需要枚举停摆原因。** 旧实现靠 `onAutomaticConditionLost()` 上报「暂停开始」，必须覆盖循环存活条件的全部来源，漏掉任何一条（例如扩展 Binder 掉线）都会让恢复后的旧内容写进剪贴板。现在任何原因的停摆都只表现为「补查时云端那份内容的生成时间已经很老」这一个事实，与原因无关。以下情况仍会触发降级路径的基线重建，且这些条件不影响主判据：

- 锁屏后重新解锁
- 网络恢复或重新满足仅 Wi-Fi 条件
- 自动远端接收关闭后重新开启
- `:sync` 进程重新启动
- 用户关闭「接收暂停期间的云端更新」

关闭暂停接收时，进入锁屏或失去网络条件还会清除尚未完成的远端剪贴板写入，防止旧内容在恢复后越过判据。

SyncClipboard Server 3.x 提供带时间的接口：`GET /api/time`（服务器时间）、`GET /api/history/{Type}-{Hash}`（含 `createTime` / `lastModified`）、`POST /api/history/query`。但**当前剪贴板通道没有时间字段**——`/SyncClipboard.json`、`/api/current`（该路由实际不存在）与 SignalR 推送都只有 `type`、`hash`、`text`、`hasData`、`dataName`、`size`。因此内容时间只能由历史接口回查，而历史默认只保留 7 天、最多 1000 条，超出后判定自动降级。`createTime` 是内容**到达云端的时刻**，不是它在源设备被复制的时刻；同一 Hash 重复上传只刷新 `lastModified`，不刷新 `createTime`——所以只能用 `createTime` 判断旧新，用 `lastModified` 会得到恒定偏新的错误结论。

暂停期间发生 `A → B → C` 且前两项已被覆盖时，客户端恢复后只能观察并处理 C，无法还原 A、B。

## 下载去重判据

「这份远端内容要不要写进剪贴板」的判据是**本机剪贴板里现在是不是已经有它**，而不是「这个哈希以前同步过没有」。

- 本机剪贴板内容在本地复制上报（`onClipboardText`）与每次写入剪贴板成功之后登记为 `local_clipboard_hash`，哈希算法与上传完全同源（`PayloadFactory.textHash`，trim 后 SHA-256）。它表达的是「剪贴板里是它」这一本机事实。
- 文本路径上，登记值等于远端内容哈希时不做任何处理，并记一条 `remote_deduped` 诊断事件；不相等、或拿不到（从未登记、登记之后设备重启过）时照常写入。**未知一律不抑制**——把内容写进剪贴板总是安全的，误抑制才会让用户拿不到内容。
- 登记值只在同一次开机内可信：重启后系统剪贴板被清空，而登记值还在。用 `SystemClock.elapsedRealtime` 随重启归零来识别，记录时刻晚于当前时刻即作废。
- 图片与文件没有可读回的本机状态，仍比对「上次同步点」`last_automatic_remote_hash`。内容时间判据不可用时的基线降级路径同样如此——那是唯一必须靠记录来阻断停摆窗口内容的情形（`needsBaselineSuppression`）。

历史版本让 `last_automatic_remote_hash` 一个字段同时充当「上次同步点」和「剪贴板里是什么」。它被上传、下载、归档三条路径共用，表达的是「这个哈希我处理过」：归档一条停摆期间到达的旧内容后它照样被对齐，于是同一份内容再被推送时会被静默丢弃——设备重启后剪贴板被清空，用户就再也粘不到它。两个语义分开之后，这类「明明推来了却没写进去」不会再发生。

补查路径上判定顺序也是固定的：**先**排除「本机已经有这份内容」，**再**判它是不是窗口里的积压。顺序颠倒会让刚同步过的正常内容在每次重连时都被判陈旧并归档。

## 待上传文本

自动上传只保留最新一条待处理文本：

- 普通文本保存在应用私有配置中，进程重启后可以恢复
- 新文本会替换旧文本，不建立历史队列
- 上传成功、关闭自动同步或关闭文本自动上传后清除
- 空白文本不进入队列
- 被标记为敏感的内容不写入持久存储

清除操作会比较待处理文本，旧任务完成时不能误删随后复制的新内容。

## 本地记录

主体应用维护两类相互独立的记录：

- 自动同步诊断记录：最多 100 条、最长 7 天，只保存时间、事件类型、内容类型和错误分类，不包含剪贴板正文、服务器地址、用户名、密码、文件名或 Hash
- 文本同步历史：默认关闭，最多 100 条、最长 7 天、总文件不超过 10 MB，保存同步方向、时间、服务器标识、Hash、完整文本及是否已应用到剪贴板

文本历史中的每条记录使用独立的 Android Keystore 密钥和 AES-256-GCM 加密。文件采用跨进程锁和临时文件原子替换；敏感自动上传文本不会进入历史。诊断记录写入或历史写入失败都不会中断同步。

同一服务器、来源和 Hash 连续重复时合并记录。远端内容先因判定为陈旧而只保存历史、随后又成功写入剪贴板时更新原条目，不新增重复项。当前不保存图片、文件或 `Group` 内容历史，陈旧内容判定也只对文本启用。

## 文件处理

手动上传支持文本、图片和单个文件。远端自动接收按元数据中的内容类型过滤，未启用的类型不会请求对应数据文件。

远端图片和文件使用流式下载：

```text
HTTP 响应流
→ 同步计算 SHA-256
→ SAF 输出流
→ 校验成功后保留文件
```

下载或校验失败时删除未完成文件。自动接收 `Group` 时当前保留压缩包；手动下载 `Group` 时执行路径检查、文件数量限制和解压后大小限制。

## IPC 与安全边界

- 系统扩展的静态作用域只有 `com.android.systemui`
- 主体应用与系统扩展使用不同 UID，不使用 `sharedUserId`
- 两个 APK 使用同一发布证书，主体应用会比较安装包签名
- Binder 服务仍会逐次验证调用 UID 对应的包名，同签名不能代替调用方校验
- 桥接协议版本不兼容时拒绝启用高级自动同步
- SystemUI 扩展会在 Binder 调用期间同步检查锁定状态并完成剪贴板写入，不会在报告成功后留下可延迟执行的主线程任务
- 临时 Binder transaction 失败不会被直接判定为 Binder death；设备保持解锁时，远端剪贴板写入按 `1 秒 → 5 秒 → 15 秒 → 30 秒`进行有界重试，进入暂停状态后按用户的暂停接收设置决定是否丢弃
- 系统扩展在锁定状态变化、本地剪贴板变化及每 5 分钟一次的主线程检查中确认 callback 注册；重复注册为幂等操作，不唤醒设备，也不重启实时连接
- 文件目录使用 SAF Tree URI 和持久授权，不依赖裸文件系统路径
- 自签名证书信任只对用户明确开启的服务器方案生效
- 服务器方案使用 Android Keystore 管理的 AES-GCM 密钥加密，旧明文配置只用于一次迁移
- 应用数据不参与系统备份，避免加密配置与设备绑定密钥分离

## 状态模型

首页从 `:sync` 进程读取真实运行状态：

- 绿色：自动同步正常运行
- 黄色：等待 Wi-Fi、等待网络、等待解锁或正在连接
- 红色：扩展、服务器凭据、认证、网络、TLS、服务器响应、文件保存或内容校验错误
- 灰色：用户主动关闭自动同步

服务器状态、扩展握手和最近同步时间分别来自真实网络检查、Binder 状态及成功同步记录。手动连接检查与同步核心共用同一套错误分类；同步核心通过 Binder 返回稳定的分类码，界面只负责映射为可操作提示，不依赖异常消息文本判断错误类型。
