## 分支 feat/motion-standards：接入预测性返回并统一页面转场

- 按用户授权在 `feat/motion-standards` 分支实施，拆成三个提交，均未推送、未发布 Release：`c592ede feat: 接入预测性返回并统一页面转场`（6 文件）、`17fa878 build: 新增预测性返回门禁并接入 CI`（3 文件）、`7fc51dc docs: 补充界面导航与动效说明`（1 文件）。
- 结构：`ui/PageNavigation.kt` 集中页面模型（`AppPage` 的 `depth` 与 `order`、`parentPage`、`isForwardFrom`）。`ui/PageMotion.kt` 集中转场参数（前景 300 ms 整页位移、背景 260 ms 走四分之一页宽、前景入场缩放 0.96、前景退出 0.90、背景 0.92、进入淡化 90 ms、退出淡化 90 ms、背景退出淡化延迟 120 ms、前景退出淡化延迟 210 ms、`FastOutSlowInEasing`）。参数取自样板应用 PixelText 的 `AppNavigation.kt`。
- 中段可读性靠参数本身保证，不加透明度到手势路径：新页 90 ms 淡入早于旧页 210 ms 的淡出延迟，手势停在中段时两页都不透明。`PageMotionTest` 把这类关系固化为回归用例，不锁具体数值。
- 手势实现：`PageGesturePhase`（IDLE、DRAGGING、SETTLING）三阶段机加 `SeekableTransitionState`。拖动期 `seekTo(progress, parent)`，松手 `animateTo` 收尾后才提交 `currentPage`，取消时只退回 IDLE 并把恢复交给 IDLE 分支（不在已取消的协程里另起动画）。顶部栏手势期间跟随 `transition.targetState`。
- 关键坑：`Transition.AnimatedContent` 的 zIndex 只有目标内容能带，且相等时后加入者在上，因此返回必须给负值（本项目用 ±1f），否则当前页向外退出会被上一页盖住。
- 官方 Wear 样例（`PredictiveBackNavHost.kt`）的 `inPredictiveBack` 在 `previous == null` 时会永久卡在 true，属既知瑕疵。本实现改用「手势结束后共享 `progress` 保持 1f」的自洽写法绕开，不需要跳过标志。
- 清单加 `android:enableOnBackInvokedCallback="true"` 与 `tools:targetApi="33"`（不加 tools 会触发 lint `UnusedAttribute`，minSdk 29）。

- 用户指出：扩展版本号不必跟着主应用更新，只有需要更新时才更新，两者版本号不同也能用。README 原表述（「版本号一致，请一起下载同一版本」「本体与扩展来自同一正式发布版本，更新时请将两者一起更新到同一版本」以及「配套」）会让人以为必须同步更新。
- 改 README 共 5 处，统一为「两者版本号不必相同，主体应用更新后可以继续使用原来的扩展，扩展只在自身有更新时才需要替换」，并去掉「配套」这类暗示必须匹配的说法。`docs/architecture.md` 里的「桥接协议版本」指协议版本，不是应用版本号，未动。
- 提交 `c73e441`，推送 master。
- **构建层面未改**：两个模块仍共用 `gradle.properties` 的版本定义，同一次 Release 中两者版本号必然相同。若日后要让扩展有独立版本号，需要拆开版本定义并调整发布流程与 `verify-release.sh`。
- 另：用户提到的「扩展图标没跟着改」经核实不是代码问题。两个 APK 的图标资源完全一致（5 档 `ic_launcher_foreground` PNG 的 SHA-256 逐个相同，扩展 APK 里 5 个 PNG 全部与主体同哈希）。设备上装的是通过 Obtainium 导入的旧版扩展，所以显示旧图标。

## 主体与系统扩展拆分版本号

- 需求：扩展版本号不必跟主体走，只在扩展自身有改动时才更新，一次 Release 可能只含主体，也可能只含扩展。
- 设计（用户先选了共用递增序列，随后改为「各算各的」）：主体沿用 `syncClipboard.versionCode` 与 `versionName`，扩展用 `syncClipboard.extension.versionCode` 与 `versionName`，扩展版本名带 `-ext` 后缀（当时为 `0.3.0-ext`）。标签 `vX.Y.Z` 发主体，`vX.Y.Z-ext` 发扩展，`-ext` 后缀天然避免与主体的标签重名。
- 实现：
  - `gradle.properties` 拆成两组定义。
  - `system-extension/build.gradle.kts` 改读扩展版本。
  - 根 `build.gradle.kts`：扩展 APK 用扩展版本命名，新增 `-Prelease.modules`（默认 `app,extension`）只构建选中的模块，选择为空时 `require` 直接失败。
  - `scripts/verify-release.sh`：只校验 `build/dist` 里实际存在的 APK，标签允许匹配主体或扩展的版本号，都不匹配则报错退出。
  - 工作流新增 `Resolve release modules` 步骤解析标签，`workflow_dispatch` 时两个模块都发。
- 验证：默认产出 `SyncClipboard-Kotlin-0.3.0.apk` 与 `SyncClipboard-Kotlin-Extension-0.3.0-ext.apk`，`-Prelease.modules=app` 或 `=extension` 时 `build/dist` 只留对应产物（Sync 会清掉另一个），只有扩展 APK 却传标签 `v0.3.0` 时报错退出码 1，`testDebugUnitTest` 68 项 0 失败、`lintDebug`、`assembleDebug` 通过，Obtainium 两个正则仍互斥匹配新文件名。
- 提交 `84f5b6c`，推送 master。
