# 2026-09-17 交接记录

## 场景核实：云端为 A，解锁归档，PC 再复制 A

用户问：云端是 A，解锁后手机把 A 归档不写剪贴板，然后 PC 再次复制 A，服务端会推送吗。

核实结论（只读代码，未改）：

- **服务端会推**：`PutSyncProfile` 命中已有 hash 就 `SaveAndNotifyCurrentProfile`，`RemoteProfileChanged` 无条件发。
- **手机收到后会丢掉**：`handleRemoteProfile` 到 `applyRemoteAutomatically` 第一行 `if (sourceHash == previousHash) return null`，而归档路径已把 `previousHash` 改成 A。
- **结果**：剪贴板不动、事件表不落记录（`newHash == null` 时不进）。只有当「手机剪贴板里并不是 A」（重启清空或被覆盖）时才有实际影响，那就再也粘不到 A。

全仓核实：客户端**没有**「本机剪贴板当前 hash」这类字段（`lastAutomaticRemoteHash` 与 `clipboardHash` 搜索只有一对读写加 `SystemBridgeService` 的 11 处调用）。所以推送路径上也判不出「剪贴板里是不是已经等于 A」。修的前提是先有这个状态，且它与「暂停期间不接收」是**两件事**，属去重策略。

## 修复：下载去重判据从「上次同步点」改为「本机剪贴板事实」

用户确认这是功能设计缺陷，要求补全。改动：

- `PayloadFactory.textHash(text)`：文本哈希与上传同源（trim 加 SHA-256），登记本机剪贴板用它。
- 新增 `data/LocalClipboardState.kt`：`usableHash(nowElapsed, recordedElapsed, hash)` 纯函数，用开机计时器随重启归零识别登记值失效。`SettingsRepository` 新增 `local_clipboard_hash`（加 `_elapsed_millis`）读写。
- 登记点三处：`onClipboardText`（本地复制，含开关关闭与敏感内容的情况）、`writeClipboardText` 成功、延迟写入重试成功。
- 新增 `SystemBridgeService.remoteContentAlreadyPresent(...)`：文本看剪贴板登记值，拿不到就不抑制，命中时记 `REMOTE_DEDUPED`。图片与文件，以及「选项开着且时钟偏移拿不到」（`needsBaselineSuppression`）的情况，退回 `previousHash`。
- **删除** `staleRemoteContentAgeMillis()` 里的 `previousHash` 豁免，补查路径改为「先判本机已有、再判陈旧」。保留豁免会让归档过的内容在下一次补查绕过陈旧判定被写进剪贴板。
- `ClipboardTransferService.applyRemoteAutomatically` 去掉抑制参数（改由调用方判），`applyRemoteTextIfChanged` 改名 `applyRemoteText`。
- `AutomaticSyncEventStore` 加 `REMOTE_DEDUPED("remote_deduped")`，`MainActivity` 加文案，`docs/architecture.md` 新增「下载去重判据」一节。
