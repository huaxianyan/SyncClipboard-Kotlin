# 2026-09-16 交接记录

## 复核「接收暂停期间的云端更新」关闭后仍写入旧内容

用户反馈：关闭该开关后仍出现两次「解锁后立刻写入远端内容」。做了一次完整的代码加真机取证复核。

结论不是部署问题（两个 APK 都是 0.1.9，SystemUI 启动时间晚于扩展安装，修复已生效，设置项也确实为 false）。失效点在「是否需要建立恢复基线」的判断上，而不是写入前的哈希比较。

事件表的判据：`pollRemoteClipboard()` 记录 `download_succeeded` 时**不带内容类型**，推送与重试都带 `Text`。整个事件文件里只有两条不带类型，都在 `realtime_connected` 后 2 到 3.5 秒，即连接后立刻补查并写入，正好是那「两次」。

四个缺陷：

- H1：循环因扩展 Binder 掉线而停止不计暂停，`disconnectSystemBridge` 不调 `onAutomaticConditionLost`。
- H2：`markBaselineEstablished()` 无 epoch 保护，陈旧基线会清掉新暂停的标记。
- H3：基线哈希只走 `MODE_MULTI_PROCESS` 的 `apply()`，`reloadConfiguration()` 重建 repository 可能回滚。
- H4：推送与写入重试路径不复查策略。

诊断盲区：基线成功时不打日志也不记事件，导致事后无法归类。

## 修复：暂停恢复后仍写入远端旧内容

根因确认：`shouldRunRemoteSync()` 的五个存活条件里，**扩展 Binder 存活**这条从未上报 `onAutomaticConditionLost()`，此前只补了锁屏与断网两条。`disconnectSystemBridge()` 不通知策略，于是循环因扩展掉线停摆后重建时 `baselineRequired` 仍为 false，跳过基线直接 poll，把停机期间云端的旧内容写进剪贴板。

主修复思路定为**不枚举原因**：在 `requestRemoteSyncRestart()` 用 `wasRunning` 判断循环是否从停摆态重启，是则一律要求重建基线。这样以后新增任何存活条件都不会再漏。

另外修掉：基线建立无代际保护（阻塞 HTTP 期间发生新暂停会被陈旧完成清标志）、`requestClipboardWriteRetry` 预算耗尽后不清待写内容、扩展掉线时不清待写内容。补诊断事件 `baseline_established` 与 `stale_write_skipped`，解决「基线成功时既不打日志也不记事件」的盲区。

事件表本身不可信：非成功事件有「与上一条同状态则丢弃」的抑制，且扩展连断事件异步落盘会乱序（实测 36 毫秒内 connected、disconnected、connected）。判据改用「`download_succeeded` 是否带内容类型」，不带即 poll 路径。

服务端能力结论：官方当前剪贴板接口（`/SyncClipboard.json`）与 SignalR 推送**都不带时间**，带时间的是 `GET /api/time`（服务器时间）与 `GET /api/history/{Type}-{Hash}`（含 `createTime` 与 `lastModified`）。已实现探测式查询作为第二道防线，拿不到就完全不介入写入决策。`/api/current` 曾误认为存在，实测 404，官方源码里也没有这条路由。

校验：`testDebugUnitTest lintDebug assembleDebug` 全部 BUILD SUCCESSFUL。时间戳兜底与扩展掉线复现均未在真机验证。

## 实测服务端时间接口能力（SyncClipboard Server 3.2.0）

**无凭据也能画出路由表**：先请求一个肯定不存在的路径确认对照组返回 404，于是 401 表示路由存在但需认证，405 加 `Allow` 头表示路由存在但方法不符。用这招确认服务端有 `/api/time`（GET）、`/api/history/{profileId}`（GET）、`/api/history/query`（GET 与 POST）、`/api/history/statistics`（GET），而 `/api/current` 与 `/api/clipboard` 都是 404。

`{profileId}` 是 **`Type-Hash` 单段**（如 `Text-<64位大写hash>`），写成 `Text/<hash>` 会落到 PATCH 那条路由返回 405。

**三个时间字段的语义**（源码 `Mapper.ToHistoryEntity` 与 `HistoryService.AddProfile` 确认）：新 hash 时 `CreateTime = LastAccessed = LastModified = DateTime.UtcNow`，同 hash 重复上传只刷 `LastAccessed` 与 `LastModified` 并 `Version++`，**`CreateTime` 不变**。所以判断「这份内容是不是这段时间才出现的」必须用 `createTime`，用 `lastModified` 会得到恒定偏新的错误结论。

`createTime` 是**云端视角**的时间（服务器接收时刻），**不是**内容在源设备被复制的时刻，legacy 上传不带时间。保留策略默认 7 天、最多 1000 条，由 `HistoryCleaner` 后台清理，超期后查询返回 404。

**判据回代验证**：一次云端内容早 930 秒、一次早 81 秒，两次都会被 `isStaleRemoteContent` 拦下，一次正常解锁那次早 1865 秒、本就该跳过。三次结论全部与预期一致。

时钟偏移实测 65 到 170 ms（RTT 274 到 485 ms），远小于 5 秒宽限，`createTime` 连续两次查询完全一致。

解析隐患已修：服务端返回 `+00:00` 偏移加 7 位小数秒，而 `Instant.parse` 依赖的 `ISO_INSTANT` 对非 `Z` 偏移的支持是 JDK 12 才补齐的，Android 上可能静默失效。抽出 `SyncTimestampParser` 做多级回退，并刻意避开 `org.json`，它在 JVM 单测下是空壳，会让该路径无法被测试覆盖。8 个用例全部通过。

## 用内容时间把判定从「枚举原因」改成「绝对时刻」

定稿口径：恢复同步时，云端当前那份内容若比设备旧，就**不写剪贴板，但归档进文本历史**。更早的历史条目不去追溯，服务端只保留最新状态，不知道积压了多少条。

上一版判据有四个失效点，第一条是结构性的：`remoteClockOffsetMillis` 全库只有「循环启动清零」与「建基线时校准」两处赋值，判据里用它 `?: return false`。**两道防线是串联的**，不建基线，时间判据全程失效。已改为循环启动时独立校准，与基线彻底解耦。

其余三点：120 秒观察窗是拍的（已删，判定改用「循环启动时刻」作唯一界）；判据缺内容产生时刻这一端（现返回「内容早于恢复时刻多少毫秒」）；判陈旧即永久遗忘（现在同时 `archiveStaleRemoteText()` 归档进历史）。

`shouldEstablishBaseline()` 新增 `canJudgeByContentTime` 参数，时间判据可用时一律不走基线，于是「枚举存活条件」这个根因从需求上消失。

判据抽成纯函数 `StaleRemoteContentPolicy.staleAgeMillis()`，9 个用例覆盖边界（`grace`、`grace+1`、零宽限、服务器时钟快或慢 10 秒）。事件表新增第 5 段 `ageMillis`，解码由 `size != 4` 放宽为 `size < 4`，旧记录照旧解析。

已知限制：同 hash 重复上传不刷 `createTime`，所以「PC 端把一条旧内容重新推上来」会被归档进历史而非写剪贴板，客户端绕不过服务端数据模型。

校验：46 用例 0 失败，`lintDebug assembleDebug` BUILD SUCCESSFUL。真机复现仍未做。同时更正了 `docs/architecture.md` 里「Server 不提供事件序号或历史接口」这句错话。

## 查 `createTime` 是否会因重复复制而刷新，并修正判据的适用范围

用户追问「重新复制一条以前复制过的内容，中间内容有变化，难道不会刷新吗」。**答案是不会**，且这个事实暴露了上一版判据挂错了位置。

服务端三条写路径全部核过源码：`AddProfile` 命中已有 hash 只刷 `LastAccessed`、`LastModified`、`Version`，`AddRecordDto` 到 `UpdateExistingRecordDto` 里 `UpdateEntityFields` 把 `CreateTime` 取客户端的旧值，`PATCH`（`HistoryService.Update`）压根没给 `CreateTime` 赋值。**`createTime` 只在记录首次创建时写一次。**

客户端侧：官方桌面端 `HistoryTransferQueue.ExecuteUploadAsync` 先 `GetOrCreateHistoryRecord`（命中已有 hash 返回**旧**记录），再 `GetHistoryByProfileIdAsync` 查服务器，**已存在就直接标记成功、根本不传**。

只读实测（`/api/history/query`，50 条）：`version=1` 的 19 条两字段差小于 1 秒，`version>1` 的 35 条里 31 条 `lastModified` 被推到最多 6223 秒之后，`createTime` 纹丝不动。数据与源码一致。

`lastModified` **也不能用作判据**：`PATCH` 会把它刷成 `UtcNow`，而 `PATCH` 只同步 starred 与 pinned 与 version，不改「云端当前是哪份内容」，会出现「旧内容被标了个星就看起来是新的」从而误写。

**上一版的两个错误**（都是回归）：判据套在了实时推送上（推送里若带的是重新复制的旧内容，`createTime` 很老，被误判成积压而不写剪贴板），锚点用了 `remoteSyncLoopStartedAt`，而它在 `while` **外**赋值一次，循环内部只是反复重连，一轮可能跑好几天，于是任何早于循环起点一小时的内容都判陈旧。

改法：推送路径**移除**陈旧判定（推送只由别的设备刚 `PUT` 完触发，本身就是「刚刚」的证据），补查路径锚点改为 `System.currentTimeMillis()`，删除失效的 `remoteSyncLoopStartedAt` 字段，`StaleRemoteContentPolicy` 参数 `recoveryAtMillis` 改名 `judgedAtMillis`。

校验：47 用例 0 失败（`StaleRemoteContentPolicyTest` 增至 10 例，含一个记录「重复制与积压在时间上同形」的用例），`lintDebug` BUILD SUCCESSFUL。

## 确认「复制 A、B、C、再复制 A」两个 A 的 hash 是否相同

用户追问的是「完全相同的 A 重复复制」这一情形。**答案：hash 逐字节相同。**

依据在客户端侧：`PayloadFactory.text()` 里 `normalized = text.trim()`，`hash = sha256(normalized.toByteArray(UTF_8))`，`sha256()` 用 `%02X` 输出十六进制大写。输入只有内容本身，没有时间、设备、序号参数，所以同一段文本在任何时刻、任何设备上算出的 hash 恒定。

因此服务端 `AddProfile` 命中已有 hash 就复用同一条记录，`createTime` 停在第一次 A 到达云端的时刻，只刷 `LastAccessed`、`LastModified` 和 `Version++`。50 条实测里同一 hash 的记录只有一条、`version` 涨到 27、`createTime` 与 `lastModified` 相差 5990 秒，正是这个行为。

边界：`trim()` 使首尾空白不进 hash（A 与「A 加尾随换行」同一条），超过 10 KB 的长文本走文件通道但 hash 仍按全文 trim 后计算、不含文件名，图片与文件的 hash 是 `sha256("文件名|内容SHA256")`、文件名参与。

意义：这正是「重新复制旧内容」在服务端与「积压内容」不可区分的根因，也是判据只能留在补查窄窗口、不能上推送路径的原因。

## 核实服务端在「A B C A」下到底留下了什么时间信息

用户把问题收窄为：**服务端给出的信息里，有没有东西能辨认前后两个 A 的时间差。**

拉了上游源码逐行核实（`Jeric-X/SyncClipboard` master）。

**关键更正**：legacy `PUT /SyncClipboard.json`（`SyncClipboardController.PutSyncProfile`）并不是直接调 `AddProfile`，它先 `if (!string.IsNullOrWhiteSpace(dto.Hash))` 调 `GetExistingProfileAsync()`，命中就 `SaveAndNotifyCurrentProfile()` 返回，**根本不进 `AddProfile`**。而 `GetExistingProfileAsync`（`HistoryService.cs:295-313`）里是 `entity.LastModified = DateTime.UtcNow; entity.LastAccessed = DateTime.UtcNow; entity.Version++;`，即「重传一个已有 hash」实际刷新的是这两个时间加 `Version++`，`CreateTime` 不动。结论不变，但路径记错了要改。

**`version` 不是上传次数**：`HistoryService.Update`（PATCH，`:34-77`）里 `dto.Version ??= existing.Version + 1; dto.LastModified ??= DateTimeOffset.UtcNow;`，然后 `existing.Version = dto.Version.Value`。标星、置顶、删除标记这类与内容无关的操作也会把 `version` 加一并刷 `lastModified`。所以 50 条里 `version=27` 那条不能证明重传了 27 次。

`GET api/history/{profileId}` 到 `GetByTypeAndHashAsync`（`:281-293`）是**纯读**，不写库，用 `getRemoteContentTimestamp()` 查询不会污染服务端字段。

结论：**没有专用于此的信息。** 唯一会动的时间痕迹是 `lastModified`（`lastAccessed` 同步被刷），语义是「最近一次被触碰」，触碰来源至少三类（重传、PATCH、`POST /api/history` 更新分支），同一个字段值无法区分来源。理想情况下 `lastModified - createTime` 等于「第二个 A 比第一次晚多久」，但无法验证这期间没有别的触碰。唯一能确定「第二个 A 刚刚到达」的是**推送事件本身**，它的到达时刻不在任何字段里，这正是当前实现依赖「推送必是刚刚」的依据。

**实测佐证（只读）**：`GET /SyncClipboard.json` 实际返回的键为 `dataName, hasData, hash, size, text, type` 六个，**零时间字段**（与 `ProfileDto.cs` 的 7 个属性完全对应，`TransferDataHash` 为 null 时省略）。同一 hash 查 `GET /api/history/Text-<hash>` 才有时间：该条 `createTime = 11:59:31Z`（首次到达），`lastModified = lastAccessed = 15:29:53Z`（晚了 1 小时 30 分），`version = 3`，当次查询时服务器时间为 `15:37:04Z`。即**内容没换、时间被刷、来源不明**，这就是 `lastModified` 不能作判据的现场证据。

结论：当前剪贴板通道（legacy json 与 SignalR 推送用的是同一个 `ProfileDto`）**在协议层就没有时间位**，「这份内容什么时候出现的」只能靠另一次历史查询间接推断，且只对「云端从未见过的新 hash」成立。

## 确认「服务端与其他客户端都不动」时，Android 端的解空间

用户定调：**服务端不能动、其他平台客户端不能动**，只能在 Android 端本地想办法。

结论：**这个缺口在本地无解**，因为能消除它所需的信息在协议层就不存在。三条硬约束：

1. 窗口等于存活条件不满足期，也就是本机与云端**真的断开**（循环都停了），窗口期间的到达事件本机根本观测不到。
2. SignalR **不重放**离线推送，所以恢复后只能主动补查，补查拿到的是「当前状态」而不是「事件」。
3. 现有字段里 `createTime` 只记首次到达，`lastModified` 混用（上传与 PATCH 都刷）。

本地能调整的只有**缺口的形状**：

- ① 现状（严格）：补查只认 `createTime` 落在最近 5 秒内的内容，实际上补查约等于只归档不写。代价是补查窗口里重传的旧内容不写。最符合「宁可漏写、不误写」。
- ② 放宽：把 `lastModified ≈ now` 纳入判据，能覆盖重传场景，但会把「刚被标星的旧内容」误写，与既定口径相反，不推荐。
- ③ 把不确定性交给人：判为陈旧的内容不静默归档，而是在应用内标记「暂停期间到达，未自动写入」，可一键写入。纯 Android 端改动、零协议风险、不误写也不丢内容。

另一个务实动作：先**量化缺口的真实频率**再决定值不值得动协议。事件表里 `download_succeeded` 不带内容类型即 poll 路径，历史实测只有 2 次，且都是 bug 现场。

## 关于 `lastModified` 的精度更正

用户追问 `lastModified` 能否确定「最后的时间」。做了一次精确统计（只读 `/api/history/query`，50 条，用 `datetime.fromisoformat` 算精确差值）。

**精度更正**：服务端存的是 **100 纳秒**精度（`2026-09-16T11:59:53.7544814+00:00`），不是此前说的「秒级」。此前「同秒重传所以看起来相等」的解释因此作废。

`LM - CT` 分布（50 条）：小于 0.05 秒 6 条、小于 1 秒 14 条、小于 60 秒 5 条、小于 600 秒 3 条、大于等于 600 秒 22 条。前面几档里有 **`version` 很高但差值极小**的记录：`78D05DAD` v8 差 43 ms、`C8426145` v4 差 45 ms、`25308034` v6 差 38 ms、`BFF02090` v7 差 45 ms。

解释：这些不是 legacy 重传（legacy 每次命中都刷 `LastModified`，差值会拉大），而是 `POST /api/history` 路径，`UpdateEntityFields` 把客户端送来的 `CreateTime`、`LastModified`、`Version` **原样写库**，所以字段值可能是**客户端本地的旧值**。大于等于 600 秒的 22 条才是被 legacy 重传一路刷新的。

因此 `lastModified` 不可用的理由从「会被 PATCH 刷」升级为三条：非接收操作（PATCH）也会刷，不被触碰就不更新，**写入方可以覆盖成任意旧值**。既不能证明「最后接收」，也不能证伪。

## Android 本地归档不写的困难在哪

用户问：单纯 Android 端，恢复同步后拿到云端剪贴板，未开选项就归档进历史不写入，有什么困难。

**动作层零困难**：`SystemBridgeService.pollRemoteClipboard()` 已经是这个逻辑（`staleAge != null` 就归档进文本历史、把哈希改成那条内容、记 `STALE_WRITE_SKIPPED` 事件，返回 null 不写）。

**难的是判定「这份内容算不算窗口里积压的」**，三处信息缺口：

1. 「恢复」事件本机不一定观测得到。`requestRemoteSyncRestart()` 只在**循环从停摆里重启**时通知策略，实时通道断了但循环仍在跑（走 `FALLBACK_POLL_INTERVAL_MILLIS` 补查）、或被系统冻结后继续运行，都没有重启事件。所以判据不能挂在「恢复事件」上，只能挂内容时间。
2. 窗口起点（失联时刻）本机可能永远没记录（进程被杀、关机、崩溃），只能拿终点（判定时刻）去减内容时间。
3. 内容侧只有 `createTime`（首次到达），重传内容失真。

**最要紧的是第四点，它是行为冲突而非技术困难**：`deviceUnlocked` 是五条存活条件之一，锁屏等于循环停、SignalR 断、推送收不到。所以解锁后第一次补查拿到的那份内容，`createTime` **必然早于解锁时刻**，只要早过 5 秒宽限（几乎必然）就判陈旧、归档不写。

由此本地唯一可调的旋钮就是宽限阈值 `STALE_CONTENT_GRACE_MILLIS`（现 5 秒）。放大到分钟级可保住日常粘贴，代价是「失联 20 分钟后想粘 11 分钟前的内容」会漏写。

附注：归档通道有前提 `TextSyncHistory.record(enabled = settings.textHistoryEnabled)`，用户没开文本历史时「归档」等于丢弃，图片与文件没有历史通道，仍按原流程直接写。

## 上游 issue #427

用户在 `Jeric-X/SyncClipboard` 提了 issue **#427**（标题「请问一下现在有接口能看到最后一次同步的时间吗？」）。Jeric-X 回复：**「暂无，之后可以加一个」**，与本地源码核查、实测结论一致。

影响评估：

- **会解决**：补查路径上「重传的旧内容」与「积压内容」同形，只要新字段语义是「本次接收时刻」而非 `createTime` 那种「首次到达」。
- **不会解决**：窗口起点不可知（`deviceUnlocked` 是存活条件，解锁后第一次补查拿到的内容到达时刻必然早于解锁时刻），「锁屏期间别的设备复制 → 解锁手机粘贴」仍被拦。

客户端接入成本预估两处：`ClipboardPayload` 加字段解析、`getRemoteContentTimestamp()` 加优先链（payload 字段 → history `createTime` → null 降级）。现有探测式三级降级设计不用改。

风险提示：官方若把它做成第二个 `lastModified`（被 PATCH 刷新、允许写入方覆盖）就等于没加。已写好一段可直接回帖的说明，把字段语义钉死（专属接收动作、不被无关操作刷新、最好放进 `GET /SyncClipboard.json` 与 SignalR 推送）。

状态：等待官方，未动手改客户端。

## 撤回「主路径必被拦」的错误结论，并量化真机时序

此前曾断言「该选项开启后，锁屏期间在电脑复制、解锁手机粘贴必被拦」。用户指出这个前提是错的：正常流程就是**先解锁、再复制**，锁屏期间在电脑复制本来就不是他的用法，**那本来就该拦**。

核实成立：解锁 → `requestRemoteSyncRestart()` → `runRemoteSyncLoop()` → `client.start()`（SignalR 连上）→ 补查。通道就绪后复制的内容走**推送路径**（`handleRemoteProfile`，明确不判陈旧），正常写入。

**真机量化**（取 `files/automatic-sync-events-v1` 快照）：

- `extension_connected` 到 `realtime_connected`：199、202、232、265、269、313 ms（6 组）。
- `realtime_connected` 到补查完成（无类型 `download_succeeded`）：2257、3476、5305 ms（3 组）。
- 即解锁到通道就绪约 0.2 到 0.3 秒，解锁到补查判定约 2.5 到 5.5 秒。

由此判定：**5 秒宽限够用，不必改**。误拦需要「解锁后 0.2 秒内就复制完」且「补查慢到 5.5 秒」同时成立，手动操作不可能。重传缺口同理，只在「复制恰好早于补查请求发出」时触发。

**顺带纠正事件表读法**：`DOWNLOAD_SUCCEEDED` 只在 `newHash != null`（内容真的变了）时记录。上面 6 组 `realtime_connected` 里只有 3 组后面跟了补查记录，其余是**内容未变**，不是「没补查」。

结论：该选项的行为符合预期，拦的就是「本机看不见云端那段时间里到云端的内容」，正常「先解锁再复制」不受影响，宽限维持 5 秒。
