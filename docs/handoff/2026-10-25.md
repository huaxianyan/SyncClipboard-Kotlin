## 核实上游「最后一次同步时间」与自建服务器的落地情况

用户提到上游采纳了建议并关闭 issue，要求确认是否已经发布到在用的服务器。核实结论：已落地并已生效。

### 上游

- issue #427 于 2026-09-16 提出，2026-10-09 以 `completed` 关闭，对应提交 `d9f60d2e`（`feat: 为远端剪贴板添加带时区偏移的同步时间`，PR #477）。
- 实现方式是在 `SyncClipboard.Shared/ProfileDto.cs` 新增 `DateTimeOffset? SyncedAt`，序列化时为空则省略。`SyncClipboardController.SaveAndNotifyCurrentProfile` 在保存当前剪贴板时赋 `DateTimeOffset.Now`，写进数据根下的 `SyncClipboard.json`，并通过 `RemoteProfileChanged` 一并推给 SignalR 客户端。
- 官方服务器忽略客户端 PUT 的 `syncedAt`，一律用服务器时间。WebDAV 与 S3 没有服务端，由客户端在推送时设置。官方文档注明客户端时钟可能不同，**不应**用该字段判断并发写入顺序。
- 版本归属：`d9f60d2e` 在 `v3.3.1` 之后 5 个提交，`v3.3.2` 与 `v3.3.3` 都已包含，两者均于 2026-10-18 发布。

### 自建服务器

- 容器 `syncclipboard-server`，镜像 `jericx/syncclipboard-server:latest`，`RestartPolicy=unless-stopped`。
- 镜像构建时间 2026-10-18T08:26:56Z，容器启动 2026-10-18T17:04:31Z。部署镜像 `sha256:21fb2090…` 与 Docker Hub 当前 `latest` 一致，`latest` 与 `v3.3.3` 指向同一批按架构摘要，因此运行的是 `v3.3.3` 那一版载荷。
- 容器内 `SyncClipboard.Shared.dll` 含 `SyncedAt` 元数据，`SyncClipboard.Server.Core.dll` 含 `SyncedAt` 成员引用，说明功能已编译进去。
- 数据文件 `/srv/syncclipboard/syncclipboard-server/server/SyncClipboard.json` 于 2026-10-25T09:21:42Z 写入，含 `"SyncedAt":"2026-10-25T09:21:42.3251447+00:00"`，说明新代码路径确实在跑。服务器时区为 UTC，偏移写作 `+00:00`，小数秒 7 位。
- 只做了只读检查：没有重启容器、没有改配置、没有读取剪贴板正文（只统计字段名与时间值）。

### 对客户端的影响

- `ClipboardPayload.fromJson` 用 `optString` 按需取字段，多余的 `syncedAt` 会被忽略，现有 `v0.3.0` 解析不受影响。
- 现成判定路径仍走 `GET /api/history/{Type}-{Hash}` 的 `createTime`。`SyncTimestampParser` 已能处理带偏移与 7 位小数秒的时间，接 `syncedAt` 可复用。
- `SyncClipboardClient.getRemoteContentTimestamp` 的注释写着「官方服务端的当前剪贴板接口与 SignalR 推送都不携带时间」，**该说法已过时**，接入时一并改。
- 语义差异需先定案：`createTime` 是首见时刻，同 hash 重复推送不刷新。`syncedAt` 是最近一次提交时刻，会刷新。暂停恢复判定要用哪一个，属于设计决策，不在本次核实的范围。

## 暂停窗口判定改用 syncedAt

上游落地 `syncedAt` 后，把「不接收暂停期间的云端更新」的判定从 `createTime` 口径换成暂停窗口口径。用户确认三点：推送与补查统一判定、容差 1 秒、图片与文件暂不动。

### 改动（`cc90d94`）

- `ClipboardPayload.syncedAtMillis`：由 `SyncTimestampParser.parseSyncedAt()` 用正则提取，不走 `org.json`（它在 JVM 单测里是空壳）。
- `PauseWindowPolicy`：纯函数，输入提交时刻、恢复时刻、时钟偏移与容差，返回跳过（带年龄）、正常、不可判定三态。容差 `PAUSE_WINDOW_TOLERANCE_MILLIS = 1_000`。
- `SystemBridgeService`：循环从停止态重启时记下 `pauseWindowStartMillis`，推送与补查统一走 `applyRemotePayload`。
- 降级链：`syncedAt` 缺失时补查退回 `createTime`（宽限仍是 5 秒），**推送退回原行为不判**。理由是 `createTime` 分不清「重新提交的旧内容」与积压内容，拿它判推送会误杀用户刚复制的内容。两条都没有时仍走哈希基线。
- 文档：`docs/architecture.md` 的「暂停与恢复边界」改写，`DECISIONS.md` 的暂停恢复判定与内容时间语义同步。

### 设计取舍

- 恢复时刻只在循环从停止态重启时记录。设置变更触发的重启不重置窗口，否则每次保存设置都会把刚推来的内容推到窗口之外。
- 用户关闭「接收暂停期间的云端更新」时，若循环正在运行，不额外重置窗口。此时若 `syncedAt` 可用，基线本来也会被跳过（既有行为），所以没有引入新的不一致。
- 只对文本生效，图片与文件维持原样落盘。

### 验证

- 本机无法构建：`JAVA_HOME` 指向不存在的目录，机器上也没有装 Android SDK。改用仓库 CI 验证。
- CI 运行 `40190997772` 通过：`testDebugUnitTest lintDebug assembleDebug`、发布说明门禁 6 项、预测性返回门禁 14 项。`release` 任务按预期跳过。
- 新增单元测试：`PauseWindowPolicyTest` 10 项（窗口边界、容差两侧、时钟偏移换算、缺参数、非法容差），`SyncTimestampParserTest` 新增 4 项（真实 `syncedAt` 值、大写字段名与数字形式、正文伪字段不误取、缺失返回 null）。
- 未做：真机验证。需要一台装了 `v0.3.0` 与 `v3.3.3` 服务端的设备，实测「锁屏期间在电脑复制 → 解锁」与「解锁后立刻复制」两条路径。本机当前无可用 ADB 设备。

### 遗留

- 上传路径不写 `syncedAt`。官方服务器会用自己的时间覆盖，WebDAV/S3 才需要客户端写，等有实际需求再补。

## 暂停窗口判定的真机验收

设备 Pixel 10 Pro（`blazer`，Magisk root）已连到本机。装了 CI 用 `workflow_dispatch` 出的正式签名包（同一签名覆盖升级，配置与历史都保留），在真实服务端 `v3.3.3` 上跑通两条路径。

### 怎么装的

- 本机没有生产签名材料，debug 包会因签名不同必须卸载重装，会丢服务器配置与历史。
- 改用 `gh workflow run build.yml --ref master`：这个入口构建并上传正式签名 APK，只有打标签时才创建 Release 页面。产物 `SyncClipboard-Kotlin-release` 下载后 `adb install -r`，`versionCode` 13 不变，属普通升级。
- 装完核对：`server_profiles_encrypted_v1` 等设置都在，`receive_paused_remote_changes=false`（本次要测的状态）保持原样。

### 验证通道

- 设备有 root，直接读 `/data/user/0/com.neko7ina.syncclipboard/files/automatic-sync-events-v1` 看诊断事件。
- Android 17 没有 `cmd clipboard get`，剪贴板正文改由 `shared_prefs/sync_clipboard_runtime.xml` 的 `local_clipboard_hash` 间接确认：拿期望文本算 SHA-256 与它比对。
- 暂停用「断网再恢复」制造，不动锁屏（设备有 PIN，adb 解不开）。这条与锁屏走同一个入口：循环从停止态重启时设置窗口起点。

### 结果

1. 基线（解锁）：PC 复制 `SC-UNLOCK-…-2258`，事件 `download_succeeded`，`local_clipboard_hash` 与该文本哈希一致，确认真写进了剪贴板。
2. 暂停窗口：断网 → PC 复制 `SC-PAUSED-NET-…-2308` → 恢复网络。事件序列 `waiting_for_network` → `realtime_connected` → `stale_write_skipped`（`Text`，年龄 32 776 毫秒）。`local_clipboard_hash` **未变**，剪贴板没有被覆盖。`last_automatic_remote_hash` 变成该文本的哈希，说明它被当成已处理并归档。
3. 恢复之后：PC 复制 `SC-AFTER-RESUME-…-2311`，事件 `download_succeeded`，`local_clipboard_hash` 更新为该文本哈希，正常写入。

时间对得上：内容在 23:00:39 左右提交，网络 23:01:06 恢复，`realtime_connected` 23:01:13，跳过判定 23:01:21。32.8 秒的年龄正好等于「提交时刻到窗口起点」的间隔，说明窗口起点落在恢复那一刻，没有被补查延迟放大。

### 真实锁屏路径（用户手动验收）

用户手动做了一次：锁屏 → 在电脑上复制 → 解锁 → 打开应用查看。事件时间轴：

- 23:51:12 `waiting_for_network`：锁屏后扩展暂停网络，自动同步循环停止
- 锁定期间在电脑复制，服务端记录提交时刻约 23:51:47
- 23:51:53 `baseline_established`：解锁瞬间服务器时钟没校准成功，先走降级基线
- 23:51:54 `realtime_connected`
- 23:52:25 `stale_write_skipped`（`Text`，年龄 6 325 毫秒），30 秒后用户打开应用

结束状态：`local_clipboard_hash` 自 23:02 起未变，剪贴板没被覆盖；文本历史文件增大约 1.1 KB，内容归档成功。

附带观察：解锁瞬间 `calibrateServerClock()` 可能拿不到服务器时间，此时先由基线把当前云端内容吃掉，几秒后窗口判定还会再拦一次。两条路径都不写入，属于设计内的降级链，没有出现误放行。若以后想省掉这次多余往返，可以在校准失败时短暂重试，不必动判据。
