# 2026-09-24 交接记录

## 更换启动图标（循环图标，app 与 system-extension）

用户放了新图标（300×300，圆角浅蓝底加白色循环箭头），要求给软件和扩展都换上。

实测素材：圆角方块 203×203（占画布 67.7%，约等于自适应图标 72 比 108），底色 `#B3D3F9`（旧的 `launcher_background` 是 `#D1E4FF`），箭头 118×120 居中，内容最大半径映射后 28.9 dp（安全圈 33 dp）。

做法：把设计稿的圆角方块对齐到 **72 dp 安全区**（而不是铺满 108 dp），箭头单独做透明前景位图，底色用设计稿自己的 `#B3D3F9`。这样箭头占网格 39%、最大半径 28.9 dp，与旧图标（约 27.7 dp）视觉分量一致，桌面上不会突然变大。

改动（`branding/res` 被两个模块共享，一处改两个包生效）：

- 新增 `drawable-{m,h,xh,xxh,xxxh}dpi/ic_launcher_foreground.png`（108、162、216、324、432 px）。
- 删除 `drawable/ic_launcher_foreground.xml`（旧双箭头矢量）。
- `values/colors.xml` 的 `launcher_background` 从 `#D1E4FF` 改为 `#B3D3F9`。
- `mipmap-anydpi-v26` 与 `v33` 的 `ic_launcher.xml` 未动（v33 的 monochrome 复用同一前景）。

前景的 alpha 是从「平涂底色加图形」的图里按投影反解出来的（像素相对底色的投影距离），并乘以设计稿自身的 alpha。圆角外侧的透明像素 RGB 是白色，不乘会在四角长出白块。

核对：两个 APK 构建通过，5 档位图在包内且与生成文件**逐字节一致**，`aapt2 dump resources` 得 `#ffb3d3f9`，badging 解析到 `mipmap-anydpi-v33/ic_launcher.xml`。

状态：未提交，图标未上真机（启动器有图标缓存，装机后看不到变化时先清缓存）。

## 0.2.0 验收与导航栏闪烁修复（真机）

### 验收：四项全过

版本定为 0.2.0、versionCode 11，写 `docs/release-notes/v0.2.0.md`，构建 release、`scripts/verify-release.sh` 输出 `Verified release 0.2.0 (11)`，装到设备。

四项真机验收全过：补查窗口陈旧内容归档、剪贴板被别的内容占用时能写回（本次修复核心）、剪贴板已是同一内容时记 `remote_deduped`、杀 SystemUI 后扩展掉线恢复。

关键手段：`TileActionActivity` 已导出，`am start -a ...action.UPLOAD` 与 `...action.DOWNLOAD` 可直接读写手机剪贴板，且**都不更新 `lastAutomaticRemoteHash`**，所以能精确构造验收状态。`cmd clipboard` 与 `service call clipboard` 在本机不可用，`dumpsys clipboard` 无输出。

### 导航栏闪烁修复与真机确认

`MainActivity` 的 `bottomBar` 原本用 `AnimatedVisibility`（fade 加 slide 加 expand 与 shrink），而页面容器 `Modifier.fillMaxSize()` 铺满整个 Scaffold（含底栏区域），于是 fade 期间导航栏半透明、内容透出，高度动画又让内容内边距反复重排。改为 `if (!showingSecondaryPage) { NavigationBar { … } }`，删掉因此不再使用的两个 `slideInVertically` 与 `slideOutVertically` import。

设备解锁后补做逐帧验证：`animator_duration_scale=5` 慢放加 `screenrecord` 加 ffmpeg 逐帧像素分析。底栏消失与出现都是**单帧（约 8 ms）完成、前后零渐变**（慢放下原 300 ms 的 fade 本应拉成约 180 帧）。设备 `base.apk` 的 SHA256 与本地 release 产物逐字节一致，确认录到的是含修复的构建。

工具坑（重要）：`screenrecord` 输出是**可变帧率**，ffmpeg 必须加 `-vsync 0`，否则帧序被重采样成恒定帧率、与源不对应。时间轴要用 `ffprobe -show_entries frame=pts_time` 的真实时间戳对齐。按帧号取图用 `select='eq(n,N)'`，`-ss` 在可变帧率视频上不可靠（会落到同一关键帧）。

### 新发现：跨进程 SharedPreferences 覆盖（未修）

主进程写任一偏好会用自己内存里的 map 重写整个 XML，抹掉 `:sync` 进程刚写的 `local_clipboard_hash`（含 `_elapsed_millis`）、`last_automatic_remote_hash`、`pending_automatic_text`。失效方向偏「多做一次」，不丢内容，但去重机制不可靠。候选修法是把这几个键移入独立偏好文件。

状态：本轮仍**未提交**。上游时间接口落地前不再动客户端。

## 0.2.0 收尾：提交、底栏滑出动画、跨进程覆盖修复

用户拍板三条：底栏需要随页面滑出、修跨进程覆盖、先提交再开新分支。

### 提交与新分支

工作树里 0.2.0 整批改动按逻辑拆成 4 个提交落在 `fix/pause-resume-baseline`：`chore: 更换启动图标为循环图标`、`fix: 修正暂停恢复期间的远端内容判定与文本去重基准`、`fix: 移除底栏进出动画避免切换页闪烁`、`chore: 版本提升至 0.2.0 并补充发布说明`。之后新建 `fix/0.2.0-followup`，下面两项改动都在这条分支上，**尚未提交**。

### 底栏改成真正的滑出动画

`AnimatedVisibility` 的 exit 与 enter 只用 `slideOutVertically{height}` 加 `shrinkVertically`、`slideInVertically{height}` 加 `expandVertically`，共用一个 `tween(300, LinearOutSlowInEasing)`，**不要 fade**，fade 期间底栏半透明会透出下面的内容（就是用户最初报的那个现象）。高度动画让 Scaffold 的 contentPadding 与底栏同步收放。

真机逐帧验收：取 screen x840 到 980、y2000 到 2410 竖条（「设置」图标列，避开页面正文与系统三键图标），逐帧统计 `luma>80` 的像素数与质心。

- 旧构建：点击后**第一帧**该列亮像素即为 0，位移过程 0 帧（真正的瞬移）。
- 新构建：质心单调下移 153 到 172 px（约底栏高度 210 px 的 73% 到 82%），中间位置 15 到 83 个，全程不透明（最亮值一直 170 到 225，没有「亮像素变少而质心不动」的淡出特征）。
- 返回方向：滑入窗口 135 ms、9 帧，末段单帧步进 11 到 1 px，符合 `LinearOutSlowInEasing`。

**时长异常（值得记住）**：代码写 300 ms，实测缩放 1× 约 126 ms、5× 约 250 到 323 ms、10× 约 691 ms，1× 到 5× 只放大 2 倍而不是 5 倍。三种缩放下位移形态、幅度、不透明度完全一致，只是时长不同，所以是系统侧时间缩放行为，不是底栏实现问题。设备该项已还原为 1.0（Android 默认）。

### 跨进程覆盖：按写入者拆偏好文件

- `sync_clipboard_settings.xml` 只由主进程写，`sync_clipboard_runtime.xml` 只由 `:sync` 写。
- 只读的一方用 `MODE_MULTI_PROCESS` 取实例（按文件时间戳重读），写入方仍 `MODE_PRIVATE`。
- 服务器配置变更用设置文件里的 `server_config_token`（UUID）让旧的自动同步点失效。
- 启动时一次性清掉设置文件里搬走的 4 个旧键。
- `ClipboardTransferService` 原来自带 `SettingsRepository(context)`（主进程语义），却在 `:sync` 进程里被实例化 5 处，改为构造器注入 repository。

双向验收：主进程写入后运行时文件 md5 **一字未变**，`:sync` 写入后设置文件 md5 **前后一致**。设计说明写进 `docs/architecture.md` 的「进程与偏好文件」一节。

状态：新分支两项改动已构建并通过 `verify-release.sh`，**未提交**。

## 底栏退场节奏（第二轮修正）

用户反馈「现在装的这个和之前不是一样吗」。先核对设备包哈希（与本地 release 逐字节一致）排除装错包，再按 **1×** 复测，问题复现：底栏顶边走完全程只用了 **42 ms**。

- **根因**：`LinearOutSlowInEasing` 是「前段冲刺加末段刹车」，约 60% 位移压在开头 20% 里。而底栏能被看见的只有「顶边扫过图标」一段（约全程 38%），在减速曲线下只占 300 ms 的约 10%，即 30 到 50 ms，和旧版 8 ms 瞬移在眼里没区别。第一轮只验证了「慢放下确实有位移」就收工，口径漏了「位移在时间轴上占多少」。
- **修法**：两个方向分开取曲线，退场 `tween(420, FastOutLinearInEasing)`、入场 `tween(300, LinearOutSlowInEasing)`，页面转场（正文加标题）显式定成 `tween(300, FastOutSlowInEasing)`，底栏退场比它长（多留一会儿再走）。常量拆成 `PAGE_TRANSITION_MILLIS`、`BOTTOM_BAR_ENTER_MILLIS`、`BOTTOM_BAR_EXIT_MILLIS`，删掉原来的 `bottomBarTransition()`。
- **复测**（判据：左边缘 x12 到 72 找「贴底的、恰好等于底栏容器色 (25,24,27)±3 的连续行段」，其起点即顶边）：退场 1× 顶边 2075 到 2407 历时 **367 ms、42 个中间帧**，入场 1× 2345 到 2075 历时 **252 ms、14 帧**。同口径（10×）可见段（顶边走到系统栏上沿 2280）从 **772 ms** 变成 **2187 ms**（2.8 倍），全程不透明。

构建 `:app:assembleRelease` 加 `:app:testDebugUnitTest :app:lintDebug` 全绿，装机后与设备 `base.apk` 逐字节一致。

状态：`fix/0.2.0-followup` 上现有三项改动，**仍未提交**。
